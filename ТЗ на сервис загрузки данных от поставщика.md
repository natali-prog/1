# ТЗ на сервис загрузки данных от поставщика

## 1. Цель

Разработать сервис, который каждую ночь забирает из API поставщика данные о новых поставках (ТТН) и остатках, проверяет их и сохраняет в PostgreSQL. При критичных ошибках сервис уведомляет администратора.

Данные нужны для аналитики в Superset: контроль остатков и планирование закупок.

Модель данных описана в актуальной ERD

## 2. Компоненты сервиса

| Компонент | Что делает |
|---|---|
| Планировщик | Запускает импорт каждую ночь (например, в 23:00), время настраивается |
| API-клиент | Запрашивает данные у поставщика, обрабатывает пагинацию и повторные попытки |
| Валидатор | Проверяет структуру и корректность данных |
| Загрузчик | Записывает данные в БД |
| Логгер | Пишет результаты запусков и ошибки в `ImportError` |
| Уведомления | Отправляет письмо администратору при критичных ошибках |

## 3. Данные от поставщика

JSON по двум методам API:

- **GET /supplies?updated_since=...**: новые и изменённые поставки (номер ТТН, дата, склад, список товаров с количеством и ценой)
- **GET /stocks**: текущие остатки по каждому товару и складу

Доступ по JWT-токену, только HTTPS. Данные приходят постранично.

Товар определяется **по названию** (`product_name`).

**Пример поставки:**

```json
{
  "supply_number": "TTN-000123",
  "supply_date": "2026-09-29T10:00:00",
  "warehouse_code": "WH-01",
  "items": [
    { "product_name": "Смартфон Model X 128GB", "quantity": 50, "unit_price": 620.00 }
  ]
}
```

**Пример остатка:**

```json
{ "product_name": "Смартфон Model X 128GB", "warehouse_code": "WH-01", "quantity": 235 }
```

## 4. Соответствие данных и таблиц БД

| Данные из API | Таблица | Поля |
|---|---|---|
| Поставка (ТТН) | `Supply` | `supplier_id`, `warehouse_id`, `supply_number`, `supply_date`, `status` |
| Товар в поставке | `SupplyItem` | `supply_id`, `product_id`, `quantity`, `unit_price` |
| Остаток | `Stock` | `product_id`, `warehouse_id`, `quantity`, `updated_at` (`store_id` остаётся пустым) |
| Название товара → наш товар | `Product` | поиск по `name` |
| Товар входит в ассортимент поставщика | `SupplierProduct` | `supplier_id`, `product_id` |
| Код склада → наш склад | `Warehouse` | поиск по `code` |

**Служебные таблицы:**

- `ImportWithSupplier`: журнал запусков (`supplier_id`, `started_at`, `finished_at`, `status`, `records_received`, `records_processed`, `records_failed`).
- `ImportError`: ошибки и предупреждения (`import_id`, `record_identifier`, `severity`, `error_code`, `error_message`, `created_at`).


## 5. Алгоритм работы

1. Планировщик запускает импорт.
2. Сервис ищет запуски этого поставщика в статусе `RUNNING`. Если такой моложе 3 часов, новый запуск не стартует. Если старше 3 часов, он помечается `FAILED` (считаем, что процесс упал), и работа продолжается.
3. В `ImportWithSupplier` создаётся запись со статусом `RUNNING`.
4. Сервис запрашивает поставки, изменённые с момента `started_at` последнего запуска со статусом `SUCCESS`. Запуски `PARTIAL` и `FAILED` окно не сдвигают, поэтому отклонённые ранее записи будут загружены повторно, когда причина устранена.
5. Запрашивает актуальные остатки.
6. Проверяет каждую запись, включая поиск `product_id` и `warehouse_id` (правила в разделе 6). Ошибки пишутся в `ImportError`.
7. Считает долю отклонённых записей. Если она больше 20%, запуск получает `FAILED`, в `Supply`, `SupplyItem` и `Stock` ничего не пишется, уходит уведомление.
8. Иначе корректные записи сохраняются в `Supply`, `SupplyItem`, `Stock`.
9. Заполняются счётчики и `finished_at`, выставляется статус.
10. При `FAILED` отправляется уведомление администратору.

**Что считается записью:** одна позиция ТТН или одна строка остатка. Если отклонена вся ТТН (например, неизвестный склад), отклонёнными считаются все её позиции.

**Статусы запуска:**

- `SUCCESS`: отклонённых записей нет (предупреждения не считаются).
- `PARTIAL`: есть отклонённые записи, но не больше 20%.
- `FAILED`: отклонено больше 20% или произошла критичная ошибка.

## 6. Обработка ошибок

| Ситуация | Код | Поведение |
|---|---|---|
| API недоступен (таймаут, 5xx) | `API_UNAVAILABLE` | 3 повторные попытки с интервалом 5 минут, затем `FAILED` и уведомление |
| Ошибка 401/403 | `AUTH_ERROR` | Без повторов, `FAILED` и уведомление |
| Ошибка БД | `DB_ERROR` | Откат, `FAILED`, уведомление |
| Сбой в середине загрузки | | Запуск закрывается по правилу из шага 2. Следующий запуск грузит данные заново, дублей нет благодаря уникальным ключам |

## 7. Уведомления

В письме: поставщик, время запуска, статус, `records_received` / `records_processed` / `records_failed`, текст ошибки.

Отправляется при статусе `FAILED`.

## 8. Нефункциональные требования

- **Масштабируемость**: данные читаются постранично и записываются пачками (по 1000–5000 строк), чтобы не перегружать память.
- **Безопасность**: токен и пароль БД хранятся в переменных окружения, не в коде.
- **Логирование**: логи с id запуска, хранение 90 дней.
- **Расширяемость**: новый поставщик подключается через конфигурацию и запись в `Supplier`.


## 9. Критерии приёмки

1. Данные из тестового JSON полностью загружены в `Supply`, `SupplyItem`, `Stock`.
2. Повторный запуск не создаёт дублей.
3. Изменённая ТТН обновляется, лишние позиции удаляются.
4. Некорректные записи попали в `ImportError`, остальные загружены, статус `PARTIAL`.
5. При превышении порога отклонённых записей статус `FAILED`, данные не сохранены.
6. При недоступности API выполнены повторы и отправлено уведомление.
7. При активном запуске второй не стартует.
8. Загруженные данные доступны в Superset.
